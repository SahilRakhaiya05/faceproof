# HH Goa Task 3 competitor audit

**Audit date:** 3-4 September 2026

**Scope:** 19 public repositories selected from the supplied [GitHub search](https://github.com/search?q=hhgoa&type=repositories&s=updated&o=desc) (about 634 results displayed on the 4 September capture) and narrower Task 3 searches.

## Method and limits

This was a source audit, not a README comparison. I recorded GitHub metadata, shallow-cloned each current default branch, pinned the inspected commit, and traced the face, discovery, candidate-verification, anchoring, and verification paths. The inclusion set comprised the strongest recently updated Task 3 implementations visible in the supplied search plus representative repositories for each recurring failure pattern; unrelated HHGoa tasks and duplicate/empty forks were excluded except where an empty or unrelated result illustrated search noise. The 19 commit-pinned repositories are exactly the four in **Strongest implementations**, ten named in **Misleading success patterns**, and five in the following “Other sampled repositories” paragraph. For the two repositories with a public transaction, I independently called `eth_chainId`, `eth_getTransactionByHash`, `eth_getTransactionReceipt`, and (where applicable) `eth_getCode` against a public RPC on the audit date.

The sample is a fast-moving hackathon snapshot, not an exhaustive census. Search ranking and repository heads can change; all implementation links below therefore use commit-pinned URLs. Stars are not a useful quality signal here: the relevant repositories checked had zero stars except `HZNPrince/hhgoa-face-chain`, which had one. Their latest pushes were 2-3 September 2026.

No competitor code was copied. A GitHub repository without a license is copyright-protected by default: its ideas may be independently reimplemented, but its source must not be copied, modified, or distributed. A README sentence saying “MIT” is not a substitute for a license grant in the repository.

## What is safe to learn, without copying code

1. Upload the image directly to the reverse-image provider when supported; avoid persistent public temporary hosts.
2. On Lens, search the full input and a face crop, record each lane/provider search ID, request `no_cache=true`, and retain a sanitized response plus exact-body digest. On Bluesky, preserve the returned AT URI/post CID/image CID and response digest; label the `bsky.app` permalink and page/capture IDs as locally derived rather than provider-issued.
3. Treat discovery as candidate generation. Download candidate media, compare every detected face locally with one pinned model and frozen threshold, and fail closed when none pass.
4. Require a real post permalink with a stable post ID. Keep profile pages—including LinkedIn—clearly labelled as leads, never Task 3 matches.
5. Require explicit consent and human review before anchoring. Keep raw face images and embeddings off chain.
6. Canonicalize evidence before hashing. Bind image/media hashes, capture time, URL, provider trace, model hashes, threshold, decision, consent reference, and policy version.
7. Verify much more than “a tx hash exists”: expected chain ID, trusted contract bytecode hash, signer, target, calldata/event, successful receipt, canonical block, confirmations, and registry read-back. Journal the exact signed transaction before broadcast so RPC ambiguity cannot create duplicate anchors.
8. Demonstrate both a no-match stop and a one-byte tamper failure. Report face-verification benchmark metrics separately from open-web search recall.

## How FaceProof is different

FaceProof deliberately combines the strongest ideas while closing the recurring audit gaps:

- It performs a local OpenCV YuNet quality-gated scan and SFace embedding, pins both model hashes, records the score and threshold, and reports a reproducible aggregate LFW baseline without claiming that LFW accuracy equals web-search accuracy ([research](RESEARCH.md), [accuracy validation](ACCURACY_VALIDATION.md)).
- Runtime discovery is either a genuine direct-image SerpApi Lens request with `no_cache=true` or a no-key scan of a runtime-supplied consented Bluesky feed. Lens Deep routes full-image exact and face-crop visual queries separately; Bluesky binds AT URI/post CID/image CID, derives the web permalink locally, and never receives the query portrait. Candidate media is independently re-matched, with no fixture fallback ([README](../README.md#architecture)).
- Discovery and anchoring are separate passes. The anchor pass replays the sealed input and search policy and makes a newly fetched provider request; only Lens claims the explicit `no_cache=true` parameter. It accepts only the exact human-reviewed permalink and content identity—AT URI/CIDs for Bluesky, or candidate/captured media hashes plus stable capture metadata for Lens. Below-threshold or changed-content results do not anchor.
- LinkedIn/restricted profiles are opt-in discovery leads only. FaceProof neither logs in nor calls a profile the matching social post required by Task 3.
- RFC 8785 canonical evidence and a fresh random-salted commitment keep raw images and face embeddings off chain. The evidence directory necessarily retains plaintext query/crop/candidate media for re-verification, while raw embedding vectors are not stored. Verification re-hashes artifacts and checks trusted chain configuration, runtime bytecode hash, transaction, receipt, event, canonical block, confirmations, and registry state ([threat model](THREAT_MODEL.md)).
- A fresh local Anvil chain provides a zero-cost, real deploy/anchor/read-back/tamper demonstration. A pre-broadcast recovery journal binds the exact signed transaction, avoiding duplicate writes after an ambiguous RPC response.

One proof gap remains before the strongest submission: the repository currently documents the Base Sepolia contract address as “set after an optional public deployment” ([README](../README.md#blockchain)). The local Anvil route satisfies the task, but a clean consented live run plus a Base Sepolia deployment, explorer transaction, complete privacy-managed evidence bundle, and fresh-process verification would make the result independently durable and put FaceProof ahead of the audited sample. Explorer source verification is an additional transparency upgrade only after the exact deployed address shows matching source/compiler inputs; it is not implied here.

## Bottom line

No audited repository recreates FaceCheck's web-scale crawler and biometric index. Every credible entry delegates discovery to Google Lens/SerpApi, Google Vision, Yandex, Lenso, or FaceCheck, then adds local verification. Rebuilding FaceCheck honestly would require a licensed crawl corpus, continuous face extraction, vector indexing, source-URL provenance, deletion/consent governance, abuse controls, and a measurable 1:N evaluation—not merely a face embedding library.

The defensible winning claim is therefore narrower and stronger: **genuine reverse-image discovery, independent local face verification, explicit human approval, and independently re-verifiable tamper evidence**. FaceProof should demonstrate that entire chain live and publish the resulting proof, rather than claim universal person identification or 100% accuracy.
